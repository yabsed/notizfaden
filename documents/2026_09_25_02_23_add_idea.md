**Svelte + Haskell, 나는 찬성이야.** 앞선 제안은 개발의 재미나 네 기술적 취향을 고려하지 않고 익숙한 스택으로 너무 빨리 정했어. 개인적으로 오래 만들어갈 제품이라면, 쓰고 싶은 기술이라는 것도 중요한 선택 기준이야.

다만 둘에 대한 추천 이유는 조금 달라.

**Svelte는 이 앱의 프론트엔드로 적극 추천할 만해.**

메모 앱은 카드, 입력창, 체크박스, 색상 선택처럼 작은 상호작용이 많잖아. 내 판단에는 HTML·CSS와 상태 변경을 가깝게 작성하는 Svelte 방식이 이런 화면을 만들고 다듬기에 잘 맞아. Svelte는 컴파일러 중심의 UI 프레임워크야. [공식 소개](https://svelte.dev/)

특히 네가 원하는 건 기존 UI 라이브러리의 기본 디자인보다 **Keep의 구체적인 여백과 카드 모양을 재현하는 것**이니까, Svelte 컴포넌트와 직접 작성한 CSS로 만드는 방식이 좋아 보여. React 참고 코드도 색상·치수·동작을 참고하는 데는 충분하고.

안드로이드도 기존 제안대로 Capacitor를 사용할 수 있어. Capacitor는 React 전용이 아니라 웹 프레임워크와 독립적으로 사용할 수 있어. 다만 Svelte로 바꿔도 WebView 기반이라는 특성은 그대로야. [공식 설명](https://capacitorjs.com/)

**Haskell은 제품의 규칙을 정교하게 설계하는 재미가 있는 선택이야.**

이 앱의 서버에서 어려운 건 메모 CRUD보다 다음 같은 규칙이거든.

- 친구를 끊은 뒤 어떤 메모에 접근할 수 있는가?
- 원본이 비공개가 되면 파생 메모에서 무엇을 보여주는가?
- 두 기기가 같은 메모를 수정하면 무엇을 보존하는가?
- 오래된 저장 요청이 최신 공개 범위를 덮어쓰지 못하게 하려면?

Haskell에서는 이런 상태와 결과를 명시적인 타입으로 표현하고, 판단 로직을 DB 처리와 분리하기 좋아.

```haskell
data Visibility
  = Private
  | Friends
  | Public

data SaveResult
  = Saved Revision
  | Conflict Note Note
  | PermissionDenied
```

이렇게 하면 저장 결과를 처리하는 코드에서 충돌과 권한 거부를 의식적으로 다루게 돼. **물론 타입만으로 개인정보 노출이나 동기화 오류가 사라지는 건 아니야.** 실제 권한 조회, 트랜잭션, 테스트는 여전히 필요해.

API는 **Servant**가 어울려. HTTP API를 Haskell 타입으로 표현하고 서버 구현을 연결하는 도구라 이 방향과 잘 맞아. [Servant 공식 저장소](https://github.com/haskell-servant/servant)

대신 Haskell을 처음 배우면서 만든다면, 메모 기능보다 타입 오류·라이브러리 조합·빌드 환경을 이해하는 데 시간을 쓰는 구간이 생길 거야. 프론트 TypeScript와 서버 Haskell 사이의 API 계약도 별도로 관리해야 하고. 이 비용을 감수할 만큼 언어 자체에 관심이 있다면 충분히 선택할 만해.

내가 지금 다시 고른다면 이렇게 하겠어.

| 영역 | 선택 |
|---|---|
| 프론트 | **Svelte + TypeScript + Vite** |
| Keep 스타일 | 직접 만든 Svelte 컴포넌트 + CSS |
| 안드로이드 | Capacitor |
| 오프라인 저장 | IndexedDB + Dexie |
| 서버 | **Haskell + Servant** |
| 서버 DB | PostgreSQL |

초기에는 브라우저와 안드로이드에서 실행되는 앱 중심이므로 Svelte + Vite로 시작하고, 공개 메모의 검색 노출이나 서버 렌더링이 중요해질 때 SvelteKit 도입 범위를 판단하겠어.

그리고 이 조합을 평가하는 첫 결과물은 거대한 기반 구조가 아니라 **“Keep처럼 생긴 카드 하나를 작성하고, Haskell 서버에 저장해서, 다른 기기에서 열고 수정하는 것”**이면 돼. 여기까지 만들면 개발 감각과 실제 복잡도를 훨씬 정확히 알 수 있어.

**Svelte는 제품에 잘 맞아서 추천하고, Haskell은 네가 그 언어로 제품을 만들어가는 과정에도 흥미가 있다면 추천해. 나는 이 프로젝트에서 둘을 함께 선택하는 게 충분히 설득력 있다고 봐.**

---

**네 우선순위가 “Keep처럼 생기고 느껴지는 앱을 빨리 만드는 것”이라면 React가 더 낫다고 봐.** 기존 `googlekeepclone`의 컴포넌트와 스타일을 직접 활용할 수 있으니까.

다만 그 프로젝트는 React 16·Snowpack 기반이라, **그대로 확장하기보다는 React + TypeScript + Vite로 새 기반을 만들고 카드·입력창·메뉴·테마를 옮기는 방식**을 추천해. 기존 코드의 저장 로직까지 그대로 가져오지는 않고.

Svelte로도 같은 디자인을 만들 수 있지만, 참고 컴포넌트를 다시 작성해야 해. 지금 네가 Svelte 자체를 배우고 싶은 게 아니라면 그 추가 작업의 이점이 크지 않아.

그리고 **프론트를 React로 바꿔도 백엔드는 Haskell + Servant로 가면 돼.** 둘은 독립적인 선택이야.

내 추천은 **React + Haskell + PostgreSQL + Capacitor**야. Keep의 디자인을 활용하면서 Haskell로 메모 권한과 동기화 규칙을 만드는 재미도 유지할 수 있어.

아직 `app`에 코드를 작성하지 않았으니 지금 바꿔도 되돌릴 작업은 없어.
